# こんだて

3か月（90日）分の献立を自動で組み、買い出しリストまで作るサイト。
冷蔵庫にあるものを入力すると、直近の献立をそれを使い切る方向に差し替える。
栄養は日本人の食事摂取基準にもとづいて計算・判定する。

サーバーもビルドも不要。ブラウザだけで動き、データは端末の中にしか残らない。

## 使い方

```bash
npm start          # http://localhost:8080 を開く
```

`python3 -m http.server 8080` を直接叩いても同じ。ES modules を使っているので
`index.html` をファイルとして直接開くと動かない（HTTP で配信する必要がある）。

1. **設定** — 食べる人の年齢・性別・活動量、期間、買い物の間隔を決めて「献立をつくる」
2. **献立** — 90日分のカレンダー。日をクリックすると材料・作り方・その日の栄養が出る
3. **買い出し** — 買い物日ごとに、売り場順のチェックリスト。印刷とテキストコピーに対応
4. **冷蔵庫** — 在庫を入れて「在庫にあわせて組み直す」。差し替えた内容と使い切り見込みが出る
5. **栄養** — 週ごとの達成率、判定の悪い日と、その日の差し替え候補

## 設計

### 何をどこで決めているか

| 層 | 役割 | 場所 |
|---|---|---|
| 食材マスタ | 100gあたりの栄養、売り場、購入単位、日持ち、旬 | `src/data/ingredients.js` |
| レシピ | 材料（食材ID × 1人前のグラム数）と手順 | `src/data/recipes.js` |
| 栄養 | 目標値の算出、栄養計算、判定 | `src/core/nutrition.js` |
| 献立生成 | 候補のスコアリング、選択、日ごとの修復 | `src/core/planner.js` |
| 買い物 | 期間ごとの集約、購入単位への丸め、在庫の差し引き | `src/core/shopping.js` |
| レポート | 週集計、指摘、差し替え候補 | `src/core/report.js` |
| 画面 | すべての表示 | `src/ui/`, `src/main.js` |

**レシピは栄養値を持たない。** 材料と分量だけを持ち、栄養は食材マスタから計算する。
レシピごとに栄養値を手で書くと、材料を変えたときに更新漏れが起きて必ず矛盾する。

**生成は決定論的。** シードから乱数を作るので、同じ設定・同じシードなら毎回同じ献立になる。
`Math.random()` を直接使っていないのでテストが書ける。

### 献立の組み方

1日ごとに、朝食 → 昼食 → 主菜 → 副菜×2 → 汁物 → 主食 の順で決める。
各段階で候補をスコア付けし、上位から重み付き抽選する。スコアに入るのは:

- その日まだ足りない栄養素をどれだけ埋めるか
- 食塩と脂質が、その食に割り当てた予算を超えないか
- 同じ主材料（肉・魚・卵・大豆）が続いていないか、調理法が偏っていないか
- 平日夜に時間のかかるものになっていないか
- 旬かどうか
- 冷蔵庫の在庫、とくに期限が近いものを使うか

**同じレシピを直近N日に出さないのは減点ではなく候補からの除外**にしている。
減点方式だと栄養スコアの高いレシピが減点を跳ね返して連日出てしまい、
重みを上げると今度は栄養が崩れる（実測で90日中82件の連日重複が出た）。

**主食の量は残りエネルギーに合わせて可変**。おかずを固定量にしたまま主食も固定にすると、
成人男性の日はエネルギーが常に不足し、かといっておかずを増やすと食塩が上限を超える。
実際の家庭がごはんの量で調整するのと同じことをしている。

決め終わった日の判定が悪ければ、**1品ずつ差し替えて直す修復パス**が走る。
生成し直すと別の日が崩れるだけなので、崩れた日だけを局所的に直す。

### 味付けの倍率

家庭料理の標準的な味付けのままだと、食塩が目標を1〜2割超える献立しか組めない
（4つの世帯構成で実測して100〜122%）。とくに子どものいる世帯は食塩の上限が
体格比では緩まないので影響が大きい。

そこで**しょうゆ・みそ・だしの素など、減らしても料理として成立する調味料の量**に
倍率をかけられるようにし、既定を0.85（ひかえめ）にしている。同じ条件で食塩が90〜110%に収まり、
要改善の日が23%から6%に減る。「レシピどおり」も選べるので、黙って薄めているわけではない。
パンや麺、ハムにもともと含まれる食塩は減らしようがないので触らない。
買う調味料の量も倍率に合わせて調整される。

### 買い物リスト

レシピが要求するのは「にんじん40g」でも、店で売っているのは1本150g。
この差を無視するとレシピ通りに買って必ず余るので、集約は次の順でやる。

1. 買い物日ごとに、次の買い物日までのレシピが必要とする量を合算する
2. 生鮮は日持ちで区切る。日持ちの範囲に入る最も遅い買い物日に割り当て、
   どの買い物日からも届かないものには注意書きを付ける
3. 冷蔵庫の在庫と、前回の買い物の余りを差し引く
4. 購入単位に切り上げる。余りは、次の買い物日まで日持ちするものだけ持ち越す
5. 売り場順に並べる（青果 → 精肉 → 鮮魚 → 乳卵 → 豆腐練物 → 米麺パン → 乾物 → 調味料 → 冷凍）

### 冷蔵庫からの差し替え

対象期間をまるごと生成しなおすと、在庫を2品入れただけで38品が入れ替わる。
利用者から見れば「献立が作り直された」のであって「在庫にあわせて調整された」ではない。
そこで**在庫を使う方向に効く差し替えだけを、1日あたり2品まで**探す。
栄養判定が下がる差し替えは、在庫をどれだけ消費できても採らない。

使い切れない在庫は使い切れないと返す。

## 栄養の基準

`.claude/skills/kondate-planner/references/nutrition.md` に基準値と判定しきい値をまとめてある。
日本人の食事摂取基準（2020/2025年版）と健康日本21の野菜摂取目標にもとづく実務値。

判定は1日単位と週平均の両方で行うが、**合否は週平均で見る**。
全11項目を毎日良好にするのは非現実的で、それを要求すると
「毎日ほうれん草のおひたし」のような栄養的には正しいが続かない献立になる。

疾患による食事制限（腎臓病のたんぱく制限、糖尿病の指示エネルギーなど）には使えない。
医師・管理栄養士の指示を優先すること。

## 現在の生成品質

3人世帯（38歳男性・36歳女性・8歳女児）、90日、既定設定での実測:

| 指標 | 値 |
|---|---|
| 判定 良好 / 注意 / 要改善 | 76日 / 8日 / 6日 |
| エネルギー達成率 | 100% |
| たんぱく質 / 食物繊維 / 野菜 | 126% / 126% / 130% |
| 食塩（上限に対して） | 108% |
| カルシウム / 鉄 | 110% / 121% |
| 使用レシピ種類 | 103 / 171 |
| 連日重複 | 0件 |
| 生成時間 | 90日で約130ms |

`npm run tune` でスコアの重みを変えたときの影響を測れる。
重みは勘ではなく、この探索で決めている。

## 開発

```bash
npm test           # 63件（データ整合性・栄養計算・生成・買い物・レポート）
npm run tune       # スコア重みの探索
```

依存パッケージなし。テストは Node 標準の `node --test` のみ。

画面まで含めた通し確認は別に用意してある（Playwright が必要）:

```bash
npm i --no-save playwright
npm start &
npm run test:e2e   # 25項目。タブ・カレンダー・買い物・冷蔵庫・栄養・保存・スマホ幅
```

## データを増やす

レシピを足すときは `src/data/recipes.js` に1行足すだけでよい。栄養は自動で計算される。
食材マスタにない食材を使いたい場合は先に `src/data/ingredients.js` に追加する。
`npm test` がデータ整合性（未定義の食材ID、ID重複、非現実的な栄養値）を検査する。

LLMにレシピを書かせる場合は `docs/prompt-design.md` の P1 をそのまま使える。
