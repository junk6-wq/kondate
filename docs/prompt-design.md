# プロンプト設計

## 0. 前提: どこをLLMにやらせ、どこをやらせないか

献立生成の全部をLLMに投げると、次の形で必ず壊れる。

- 90日 × 3食 = 270食を1回の生成で出させると、後半で品質が落ち、同じ料理が繰り返される
- 栄養値の足し算を自然言語でやらせると数値が合わない(検算できない)
- 買い物リストの単位換算(にんじん40g×5回 → 2本)を毎回言葉で計算させると誤差が出る
- 生成のたびに結果が変わり、「さっきの献立に戻して」が成立しない

そこで**責務を分ける**。

| 層 | 担当 | 実装 |
|---|---|---|
| 決定論エンジン | 献立の組合せ、栄養計算、買い物リスト集約、在庫差し引き | JavaScript(`src/core/`) |
| 知識ベース | 食材の栄養価・売り場・日持ち・旬、レシピの構成 | データ(`src/data/`) |
| LLM層 | 知識ベースの拡張、利用者の自由文の解釈、講評の言語化 | プロンプト(本書) |

エンジンが「正しさ」を担保し、LLMは「増やす」「読み取る」「説明する」の3つだけをやる。
検算可能なものを検算可能なまま保つのがこの設計の目的。

以下の4本が本システムのプロンプトである。すべて JSON 入出力で、入出力の形は各プロンプト内に直接書いてある。

---

## P1. レシピ生成プロンプト(知識ベース拡張)

**目的**: 献立の多様性はレシピ数に比例する。レシピを追加するときに、
エンジンが要求するスキーマと栄養整合性を保ったまま生成させる。

**設計上の要点**

- **栄養値を書かせない**。材料と分量(g)だけ書かせ、栄養は食材マスタから計算する。
  LLMに「このレシピは約380kcal」と書かせると、材料を変えたときに更新されず矛盾が残る。
  材料だけなら矛盾しようがない
- **食材名は必ずマスタの語彙から選ばせる**。「玉ねぎ」「たまねぎ」「タマネギ」が混在すると
  買い物リストが3行に割れる。マスタにない食材が必要なら、レシピではなくマスタ追加として別途出させる
- **1人前で書かせる**。人数倍はエンジンがやる

```
あなたは日本の家庭料理のレシピを構造化データとして書き起こす役割です。

## 出力するもの
以下のJSON配列のみを出力してください。説明文は不要です。

[{
  "id": "英数字とハイフンの一意なID",
  "name": "料理名(日本語)",
  "role": "main | side | soup | staple | breakfast | lunch",
  "protein": "meat | fish | egg | soy | dairy | none",
  "cuisine": "japanese | western | chinese | other",
  "method": "grill | simmer | stirfry | fry | steam | raw | boil",
  "minutes": 調理時間(整数),
  "seasons": ["spring","summer","autumn","winter"] のうち向いている季節,
  "servingsBase": 1,
  "ingredients": [["食材ID", 1人前のグラム数], ...],
  "steps": ["手順1", "手順2", ...]
}]

## 制約
- ingredients の食材IDは、次のマスタに存在するものだけを使ってください:
{{INGREDIENT_MASTER_IDS}}
  マスタにない食材は使わないでください。どうしても必要なら、そのレシピは出力せず
  末尾に "MISSING: 食材名" の行で報告してください。
- 分量は1人前です。調味料も省略せずgで書いてください
  (食塩相当量の計算に必要です。しょうゆ小さじ1=6g、みそ大さじ1=18g として換算)。
- 栄養価は書かないでください。材料から計算されます。
- steps は3〜6行、各行は一文。家庭のコンロとフライパンで完結する手順にしてください。

## 依頼
{{REQUEST}}
例: 「role=main、protein=fish の秋向けレシピを8品。調理法が偏らないように。」
```

**なぜ MISSING を報告させるか**: 存在しない食材IDを勝手に作られると、
エンジン側で栄養が0のまま静かに集計され、栄養不足に気づけない。
壊れたデータを黙って受け取るより、生成を止めて報告させたほうが安い。

## P2. 在庫読み取りプロンプト(自由文 → 構造化)

**目的**: 「冷蔵庫に半分使った白菜と、昨日の鶏もも2枚、賞味期限明日の牛乳がある」という
人間の書き方を、エンジンが扱える在庫レコードに変換する。

**設計上の要点**

- **量が書かれていないのが普通**。「白菜半分」→ 白菜1玉1200g の半分 = 600g のように、
  購入単位から推定させる。推定したことを `estimated: true` で明示させ、UI上で修正可能にする
- **賞味期限は相対表現が多い**。「明日まで」「そろそろやばい」を日付に変換する。
  基準日を必ずプロンプトに埋める(LLMは今日が何日かを知らない)
- **判断がつかないものは捨てずに返す**。無視すると利用者は「入力したのに反映されない」と感じる

```
あなたは冷蔵庫の中身のメモを、在庫データに変換する役割です。

今日の日付: {{TODAY}}

## 出力
JSONのみ:
{
  "items": [{
    "ingredientId": "食材マスタのID",
    "displayName": "利用者が書いた表現をそのまま",
    "grams": 数値,
    "estimated": true/false,
    "expiresOn": "YYYY-MM-DD" または null,
    "note": "推定の根拠や補足(任意)"
  }],
  "unresolved": ["マスタに該当が見つからなかった記述"]
}

## 変換ルール
- 食材IDは次のマスタから選ぶ: {{INGREDIENT_MASTER}}
  (各行は「ID / 表示名 / 標準購入単位とその重量」)
- 量の表記が曖昧なとき("半分","1袋","少し")は標準購入単位から推定し estimated=true にする。
  "少し" は標準単位の20%、"半分" は50%、"たっぷり" は100% を目安にする。
- 期限の相対表現は今日の日付から絶対日付に直す。
  "明日まで"→翌日、"今週中"→今週日曜、"そろそろ危ない"→翌日、
  期限に触れていない→null(エンジンが食材ごとの日持ちから推定する)。
- マスタに無い、または食材か判断できない記述は捨てずに unresolved に入れる。
  勝手に近いものへ寄せないでください。「鶏がらスープの素」を「鶏もも肉」にすると献立が壊れます。

## 入力
{{USER_TEXT}}
```

## P3. 栄養講評プロンプト(数値 → 助言)

**目的**: エンジンが出した達成率の数値を、利用者が行動に移せる文章にする。

**設計上の要点**

- **数値はLLMに計算させず、計算済みで渡す**。LLMの仕事は解釈と優先順位づけだけ
- **指摘は必ず差し替え候補とセット**。「食物繊維が不足しています」で終わると利用者は動けない。
  差し替え候補もエンジンが計算して渡し、LLMはどれを推すかを選んで理由を書く
- **良い点も言わせる**。全部が指摘だと利用者は続けられない。ただし嘘の褒めは要らないので、
  「良い点がなければ書かなくてよい」と明示する

```
あなたは管理栄養士として、1週間の献立の栄養評価を利用者に伝える役割です。

## 渡されるデータ
{{WEEK_REPORT_JSON}}
  - targets: 世帯の1日あたり目標値
  - daily: 日ごとの実測値と達成率、判定(good/warn/bad)
  - weeklyAverage: 週平均の達成率と判定
  - swapCandidates: 判定が悪かった日について、エンジンが計算した差し替え候補
    (置き換えるレシピ、候補レシピ、置き換え後の達成率)

## 出力
{
  "headline": "この週を一文で(40字以内)",
  "good": ["うまくいっている点。無ければ空配列"],
  "issues": [{
    "date": "YYYY-MM-DD",
    "what": "何がどれだけ足りない/多いか。必ず具体的な数値を含める",
    "why": "なぜそうなったか(献立の構成から読み取れる範囲で)",
    "fix": "swapCandidates から選んだ具体的な差し替え案",
    "swapId": "選んだ候補のID"
  }],
  "note": "補足(任意)"
}

## 書き方
- 数値は整数に丸め、達成率を併記する。例:「食物繊維 11g(目標18g / 61%)」
- issues は多くても3件。全部指摘すると利用者は何から手をつけるか分からなくなります。
  影響が大きいものから順に選んでください。
- 食塩の超過とたんぱく質の不足は、他より優先して扱ってください。
  前者は毎日積み重なると健康被害に直結し、後者は他の栄養素の吸収にも影響します。
- 断定を避ける表現("かもしれません")は使わないでください。データは確定値です。
- 疾患による食事制限が設定に含まれている場合、この講評では扱わず
  note に「医師・管理栄養士の指示を優先してください」とだけ書いてください。
```

## P4. 献立の説明プロンプト(任意・体験の味付け)

**目的**: エンジンが選んだ献立に、なぜこの組合せなのかという一言を添える。
機能上は不要だが、「自動で決まった」ものに納得感を与える。

```
次の1日の献立に、一言の解説をつけてください。

{{DAY_PLAN_JSON}}  (料理名、主材料、調理法、調理時間、その日の栄養達成率を含む)

## 出力
{"comment": "60字以内の一文"}

## 書き方
- 組合せの意図(栄養の補完、調理の段取り、旬)のうち、この献立で最も効いているもの一つに触れる。
  例:「主菜が揚げ物なので、副菜と汁物はさっぱり側に寄せています」
- 料理名を並べ直すだけの文にはしないでください。それは献立表を見れば分かります。
- おいしさの形容("絶品","ジューシー")は使わないでください。作る前の人には検証できません。
```

## 共通方針

**JSONのみを返させる**。前後に「はい、承知しました」が付くとパースが落ちる。
実装側では前後の余分な文字を落とすガードを入れるが、プロンプト側でも明示する。

**マスタの語彙を毎回埋め込む**。食材IDの一覧は数百行になるが、
省略して「適当な食材名で」とすると表記ゆれが発生し、買い物リストが割れる。
トークンを払ってでも語彙を固定する価値がある。

**失敗を報告させる経路を必ず用意する**(P1の MISSING、P2の unresolved)。
LLMに「必ず埋めろ」とだけ言うと、埋められないときに捏造する。
逃げ道を作っておくほうが、データの信頼性は上がる。

**現行実装での位置づけ**: 本サイトは P1 の出力形式で作られたレシピデータを同梱し、
エンジン単体(ネットワーク接続なし)で動作する。P2〜P4 は API キーを設定した場合の
拡張経路として定義してあり、未設定時は在庫入力はフォーム、講評はテンプレート文で代替する。
